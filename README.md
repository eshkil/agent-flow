# agent-flow

Раннер і скіли агентного флоу для GitHub-дощок Kando. Людина подає агенту сигнал з картки
в Kando: «далі» (`agent:go`) чи «переробити» (`agent:rework`). Kando визначає етап і запускає в репозиторії
workflow `kando-agent.yml`, а раннер `eshkil/agent-flow/runner@v2` виконує потрібний скіл
Claude Code з плагіна `plugin/`. Специфікація —
`eshkil/kando-board: docs/superpowers/specs/2026-10-29-agent-flow-c-design.md`.

| Етап | `agent:go` | `agent:rework` |
|---|---|---|
| Нові | triage | triage |
| Розглянуто | фіча → feature-spec, баг → bug-agent | triage |
| Спека на рев'ю | — (схвалення: `spec:approved`) | feature-spec |
| Спеку схвалено | implement | feature-spec |
| На рев'ю | pr-review | pr-fix |
| Рев'ю зроблено | merge (Approve + `ai:reviewed` + зелений CI) | pr-fix |

Раніше був ще режим A: диспетчер у самому GitHub Actions (`eshkil/agent-flow@v1`, App
`eshkil-agent`, workflow `agent.yml`). Його прибрано, бо всі репозиторії перейшли на режим C.
Тег `v1` видалено. Останній коміт режиму A — `c8b5265` в історії `main`, тож за потреби тег
можна повернути: `git tag v1 c8b5265 && git push origin v1`. Kando-майстер онбордингу сам видаляє
старий `agent.yml`.

## Як це працює

Запуск агента ініціює сам Kando, а не лейбл у GitHub: Kando викликає
workflow `kando-agent.yml` через `workflow_dispatch`, а раннер `eshkil/agent-flow/runner@v2`
міняє OIDC-токен Actions на токен GitHub App (обмежений одним репо) і промпт, запускає
Claude Code з плагіном скілів, раз на хвилину шле heartbeat (він же оновлює токен) і в кінці
доповідає Kando підсумок (успіх, збій, ліміт Claude, завислий `ai:in-progress`).
Лейблами й коментарями після запуску керує Kando.

Модель Claude (одна чи мапа «скіл=модель») задається в Kando, у налаштуваннях агента репо.

Підключення (зазвичай це робить майстер «Агент» у шапці GitHub-дошки Kando):

1. Скопіюй `templates/kando-agent.yml` у `.github/workflows/kando-agent.yml` на default-гілці
   (Kando приймає токени лише з неї). Назву файлу не змінюй.
2. Секрет репо: `CLAUDE_CODE_OAUTH_TOKEN` (`claude setup-token`) або `ANTHROPIC_API_KEY`.
   Секретів GitHub App у репо не потрібно: токен видає Kando.
3. Середовище агента опиши в `.kando/agent.yml` у корені репо:

| Ключ | Що робить |
|---|---|
| `node` | версія Node для `actions/setup-node` (напр. `'22'`) |
| `java` | версія JDK Temurin для `actions/setup-java` (напр. `'21'`) |
| `python` | версія Python для `actions/setup-python` (напр. `'3.12'`) |
| `setup` | список shell-команд, кожна окремим `bash -e` після checkout (напр. `npm ci`) |

Kando читає цей файл і передає в workflow як input `env`. Версії беруться з файлу, а не з
workflow, щоб їх міняв автор репо без правок CI.

Файли поза git (`.env`, `google-services.json` тощо) лежать у секреті репо `KANDO_FILES` —
JSON `{"<шлях>": "<вміст у base64>"}`; його створює майстер онбордингу в Kando. Workflow
передає секрет у необов'язковий input `files` (`files: ${{ secrets.KANDO_FILES }}`), а крок
`files` раннера пише файли в робочу копію **до** `setup` з правами `0600`. Шляхи лише
відносні й усередині репо: `..`, абсолютні, зворотний слеш, `.git/` та symlink-и назовні
відхиляються, причому до запису жодного файлу. У лог ідуть тільки шляхи, значення секрету
й base64 не друкуються навіть у помилках. Записані шляхи додаються в `.git/info/exclude`, щоб секретний файл не потрапив у PR широким `git add`. Без секрету (порожній input) крок нічого не робить,
тож старі `kando-agent.yml` працюють як були.

Усередині запуску `gh` і `git` автоматично користуються актуальним токеном (його оновлює
heartbeat): `bin/gh` підставляє токен з файлу, `bin/git-credential-kando` віддає його лише
для `github.com`. Скіли, що лишають PR як draft, пишуть причину в тіло PR маркером
`<!-- kando:draft-reason: … -->`.

Перед Claude крок `preflight` перевіряє запуском `git`, `gh` і `unzip`. Йде він після `setup`,
тож ці утиліти можна доставити його командами. Якщо чогось бракує, запуск завершується збоєм
без Claude, а `finish` передає перелік Kando полями `missing` і `runner_os`.

## Пріоритет проєкту у скілах

Скіли не знають стеку конкретного репо, тож на початку кожного `SKILL.md` стоїть блок
«Пріоритет проєкту»: конвенції з `CLAUDE.md` / `AGENTS.md` репозиторію (команди встановлення й
тестів, стиль, заборони) мають пріоритет над скілом; мова коментарів, PR і специфікації — мова
тікета, якщо `CLAUDE.md` не каже інакше; шлях і спосіб доказів беруться з `CLAUDE.md`, за
замовчуванням `docs/evidence/`. Службові маркери, за якими Kando розпізнає стан (`## 🔍 Тріаж`,
`❓ Потрібно уточнити`, `<sub>🤖 …`, `<!-- kando:draft-reason: … -->`, «Схвалення в Kando: …»),
пишуться дослівно незалежно від мови. Пріоритет проєкту не скасовує запобіжників скіла: гейт мерджу (`ai:reviewed` на поточному коміті, Approve людини на поточному sha, зелений CI), вимоги надати докази, маркери й заборону чіпати файли поза завданням. Їх фіксує `test/skills-neutral.test.js`.

## Автоцикл рев'ю (Kando)

Kando може вести PR автоматично: `pr-review` → `review-triage` → `pr-fix` у режимі `auto`, коло за
колом, аж до ліміту. `review-triage` читає останнє рев'ю й по кожному зауваженню вирішує
`fix` / `skip` / `human` за політикою: типова лежить у `plugin/skills/review-triage/default-policy.md`,
репозиторій перевизначає її файлом `.kando/review-policy.md`. Код він не чіпає.

Рядки промпту від Kando (у блоці «Контекст запуску (диспетчер agent-flow)», кожен окремим рядком списку):

- `- Автоцикл: коло <N> з <M>` — номер кола й ліміт.
- `- Зауваження Kando: <id> — <текст>`, де `<id>` — `CI` або `CONFLICT`.
- `- Незгода людини: @<login> з рішенням <id> «пропустити»: <примітка>`.
- `- Режим: auto` — `pr-fix` працює за рішенням `review-triage`, а не за коментарями людей. Так само він
  працює, коли людина прямо просить «виправ PR #M за рішенням розбору».

Коло `N` — номер рев'ю в ланцюжку PR: перше рев'ю — коло 1, рев'ю після `k`-го доопрацювання — коло `k+1` (може перевищити `M`); розбір і доопрацювання мають `N` того рев'ю, яке обробляють.

Коло блоку — пара `review_head` і `round` (у `kando:review` — `head` і `round`): head PR між колами може не змінитися (доопрацювання, яке нічого не виправило, не пушить), тож попереднє коло від повтору цього ж розбору відрізняє пара, а не лише `review_head`.

Незгоду людини Kando передає лише рядком промпту. Її коментар у PR підписано `<sub>🤖 Kando</sub>`, тож він
не `H` і не команда.

Скіли лишають у коментарях машинні блоки: один рядок `<!-- kando:<тип> <JSON> -->` перед підписом
`<sub>🤖 …`, а `--` у текстових полях замінено на `—`:

- `kando:review` — `{"v":1,"round":<N>,"head":"<sha>","findings":[{"id":"R1","severity":"blocking","path":"…","line":1,"title":"…"}]}`; `severity` — `blocking` або `minor`; `path` і `line` — `null` для зауваження без місця (напр. «немає тесту»).
- `kando:triage` — `{"v":1,"round":<N>,"review_head":"<sha>","decisions":[{"id":"R1","decision":"fix","rule":"P1","reason":"…"}]}`; `decision` — `fix`, `skip` або `human`.
- `kando:fix` — `{"v":1,"round":<N>,"review_head":"<sha>","fixed":["R1"],"not_fixed":[{"id":"R2","reason":"…"}]}`; `review_head` — той самий, що в виконаному `kando:triage`.

Ідентифікатори: `R<n>` — зауваження рев'ю (наскрізно в межах PR); `H<n>` — коментарі людей із правом запису, написані після розбору попереднього кола
(якщо його немає — після останнього коментаря агента перед поточним рев'ю), наскрізно в межах PR; `CI` і `CONFLICT` — із рядків «Зауваження Kando».

Стан пункту — останній довірений запис по його `id` у блоках `kando:triage` і `kando:fix`, від старих до нових: пізніший запис перекриває ранній. Так читають історію всі три скіли:
невиправлене (`not_fixed`) наступний розбір віддає людині, а `fix` після «Незгоди людини» перекриває ранній `skip`.

Якщо для `head` і `round` найновішого довіреного рев'ю немає довіреного `kando:triage`, `pr-fix` не виправляє нічого, а Kando
вважає це зупинкою, що потребує людини, а не «чекає Approve».

Довіра до блоків: машинний блок береться лише з коментаря, підписаного `<sub>🤖`, автор якого — бот
(`user.type == "Bot"`) або має `author_association` `OWNER`, `MEMBER` чи `COLLABORATOR`; блоки з інших коментарів
не враховуються. `pr-review` недовірені блоки просто не враховує; якщо ж найновіший блок рев'ю чи рішення стоїть
у недовіреному коментарі, `review-triage` і `pr-fix` зупиняються й кажуть, який коментар проігноровано, а не беруться за старіший довірений.

Цикл потребує оновленого плагіна (1.2.0) і раннера, що бере скіли з його коміту. Тег `v2` для цього
переносять лише свідомо (див. розділ «Локальні сесії Claude Code» нижче).

## Локальні сесії Claude Code (kando-session)

Коли скіл запускає не Kando, а людина у власній сесії Claude Code, Kando про це не знає:
картка не показує, що задачу хтось тримає, а паралельний запуск ▶ Агенту може зачепити ту саму
задачу. Тому кожен із восьми скілів має крок «Взяти задачу в Kando» (на початку, до будь-якої зміни
стану) і крок «Відпустити задачу в Kando» (наприкінці та на кожному шляху зупинки після взяття, зокрема де скіл чекає людину: `needs-human`, відмова в гейті). Виняток — втрачена задача: після повідомлення хука скіл зупиняється, каже людині й `end` не викликає, щоб стан лишився і перевірка перед пушем далі блокувала команди. `end` тут виконується лише за явним рішенням людини кинути задачу.
Обидва кроки пропускаються, якщо в запиті є блок «Контекст запуску (диспетчер agent-flow)»,
якщо `plugin/bin/kando-session` немає або `${CLAUDE_SESSION_ID}` не підставилась (інші редактори:
Antigravity, Gemini CLI, Codex читають ті самі `SKILL.md`, де змінні лишаються буквальним текстом).

**Скрипт** `plugin/bin/kando-session` (bash 3.2 і curl, без jq):

- `begin --session <id> --repo <owner/name> --number <N> --skill <name> [--takeover]` позначає задачу за сесією.
  Код виходу `3` — задачу вже тримає інша сесія чи запуск Kando, або `--takeover`, який сервер не підтвердив чи який не дійшов до сервера (немає токена, інший `--repo`, `400`, `401`, `403`, немає відповіді); скіл зупиняється й передає людині вивід.
  `--takeover` перебирає задачу лише в іншої своєї сесії (чужу сесію чи запуск перебрати не можна), лише за
  явним рішенням людини; скіл не вживає його з власної ініціативи. Тримається те саме репо, що в `origin`:
  якщо `--repo` не збігається з ним (людина назвала інше репо), скрипт друкує причину, виходить із кодом 0 і
  не шле запитів. Без `--takeover` усе інше (немає токена, мережа, невідомий сервер) скіл не зупиняє.
  Обмеження: розпізнається лише `origin` з хостом `github.com`; SSH-псевдонім (`git@github-work:o/r.git`) чи
  `ssh.github.com:443` дають «origin не є репозиторієм GitHub»: запиту немає, скіл працює далі без позначки.
- `end --session <id>` відпускає задачу. Після втрати задачі виконується лише за явним рішенням людини кинути
  її: це прибирає стан і знімає блокування пушів.
- `hook post-tool|pre-tool|session-end` — для хуків (нижче), JSON хука читається зі stdin.
- У GitHub Actions (`GITHUB_ACTIONS=true`) скрипт нічого не робить.

**Хуки** (`plugin/hooks/hooks.json`, підключаються разом із плагіном):

- `PostToolUse` — сигнал «сесія жива» не частіше разу на 60 с. Якщо Kando відповідає, що
  задачу втрачено (її перебрала інша сесія чи людина), хук один раз додає до контексту Claude
  вказівку зупинитись і сказати про це людині. Токен не прийнято (`401`, `403`): стан видаляється, і хук
  один раз каже, що перевірки перед пушем більше немає. Якщо, поки сесія мовчала чи була закрита, над задачею працював запуск чи інша сесія, сигнал її не
  повертає (`lost: taken_while_silent`): стан застарів, рішення за людиною, взяти задачу можна новим `begin`. Якщо ніхто не
  працював, пауза нічого не коштує. Запізнілий сигнал після кінця скіла
  (`lost: skill_done`) задачу не повертає, скрипт мовчки прибирає стан.
- `PreToolUse` (лише `Bash`) — перевірка перед `git push` і `gh pr create|edit|merge|close|ready|review|reopen|comment|update-branch|revert|lock|unlock`
  в тому самому репозиторії, що й узята задача. Таймаут 5 с: якщо Kando не відповіла вчасно, команда
  виконується. Втрачена задача — команда блокується з поясненням. Команди без `git` і `push` та без
  `gh`, `pr` і дії над PR хук відсіює без запиту; решта йде до Kando, навіть якщо пуш там лише згаданий.
- `UserPromptSubmit` — без мережі: якщо сесія досі тримає задачу, не частіше разу на 30 хв нагадує Claude, що перерваний
  скіл (Esc) тримає її далі, і просить спитати людину, чи відпустити. Поки скіл виконується, Claude просто працює далі.
- `SessionEnd` — звільняє задачу при виході; при `/clear` ще й стирає локальний стан.

**Стан** лежить у `~/.config/kando/`: `token` (токен локальних сесій з майстра в Kando),
`sessions/<session-id>` (репо, номер, скіл), поруч `<id>.beat` (час останнього сигналу), `<id>.warned`
(попередження вже показано), `<id>.pending` (сервер не відповів на `begin`, хуки повторюють його) і `<id>.refused`
(на повторений `begin` сервер відмовив, пуші заблоковано без запитів), `<id>.reminded` (час останнього нагадування). Старіші за 7 днів файли чистяться при `begin`. Адреса Kando — змінна `KANDO_URL`
(за замовчуванням `https://kando-board.pp.ua`).

**Що покриває перевірка перед пушем і межі.** Вона не розбирає shell, а шукає в тексті команди `git` разом із `push`
або слова `gh`, `pr` і дію над PR, тож ловить і heredoc, і перенесення рядків, і обгортки на кшталт `timeout` чи
`bash -c`. Команда, яка лише згадує пуш (`git log --grep=push`), теж іде на перевірку: поки задача утримується, вона
виконується, а в сесії, що втратила задачу, блокується. Не ловить пуш усередині скрипта, `make`-цілі, аліаса, іншого
інструмента чи IDE, `gh api` і команди, зібрані зі змінних; не діє без токена, без узятої задачі й для іншого
репозиторію (за робочою директорією сесії, тож `cd` у самій команді її не змінює). Це запобіжник
від випадкової гонки двох сесій, а не гарантія; рішення про перехоплення задачі завжди за людиною.

**Тег `v2` переносимо лише свідомо.** Плагін ставиться з гілки (`claude plugin install`), а `v2`
фіксує раннер режиму C у вже підключених репозиторіях. Раннер бере скіли з `plugin/` того самого
коміту, тож перенесення `v2` змінює і раннер, і скіли агента в усіх цих репозиторіях. 2026-11-17 `v2`
перенесено на коміт із закріпленням сторонніх дій за SHA (#28); попередній коміт збережено тегом
`v2-before-pin` для відкату (`git tag -fa v2 v2-before-pin^{}`). Версія плагіна — у `plugin/.claude-plugin/plugin.json`.

**Сторонні дії — за SHA.** У шаблоні й `runner/action.yml` сторонні дії закріплено за
SHA коміту з коментарем версії. Dependabot (`.github/dependabot.yml`) раз на тиждень оновлює
`.github/workflows` і `runner/action.yml`; шаблони в `templates/` він не бачить, і `test/actions-pinned.test.js`
падає, поки їх не оновлять так само.

## Локально в Claude Code

```bash
claude plugin marketplace add eshkil/agent-flow
claude plugin install agent-flow@agent-flow
```

Плагін уже стоїть? Оновіть його й перезапустіть Claude Code. Стара версія скілів не викликає `begin`, тож
навіть зі створеним токеном ▶ Агенту запустить другого агента:

```bash
claude plugin marketplace update agent-flow
claude plugin update agent-flow@agent-flow
```
