# Імплементація схваленої фічі

Працюєш **тільки** за схваленою специфікацією. Номер тікета в `$ISSUE`.
Скіл не привʼязаний до конкретного репозиторію: працюй із тим репозиторієм, у якому тебе викликали.

## Запуск від диспетчера agent-flow

Якщо в запиті є блок «Контекст запуску (диспетчер agent-flow)», це **явна команда людини**:

- `REPO`, `ISSUE`, `PR` бери з першого рядка запиту, а не з робочої директорії.
- Умови «зупинись, якщо …» з Кроку 0 не діють, **крім** закритого тікета. Захист від циклів
  («останній коментар від бота — стоп») і перевірка ідемпотентності теж не діють.
  `implement`: перевірку, що `spec:approved` поставила людина, виконуй як завжди.
- Лейбли `agent:*` не чіпай — ними керує диспетчер. `ai:in-progress` став і знімай, як описано нижче.
- **Режим `rework`**: прочитай коментарі людей, написані після твого останнього коментаря
  (підписаного `<sub>🤖`; службові коментарі `<sub>🤖 agent-flow</sub>` не враховуй), — для PR також коментарі до рядків і тіла рев'ю. Це завдання на доопрацювання.
  Опублікуй **новий** коментар у тому самому форматі з позначкою «(оновлено)» в заголовку
  і блоком **«Що змінилося»** — список змін відносно попередньої версії.
- **Доробка після мерджу** (у запиті сказано, що задачу перевідкрито після мерджу PR #N): зміни #N
  уже в `$BASE`. Зауваження виправляй у **новій** гілці від свіжого `origin/$BASE` (назва вже зайнята —
  додай суфікс, напр. `-2`) і відкривай **новий** PR із посиланням на #N. У гілку #N не пуш і його не перевідкривай.

## Крок 0. Визнач репозиторій і перевір мандат

Репозиторій бери з поточної робочої директорії, а не з памʼяті чи прикладів:

```bash
gh auth status
REPO=$(gh repo view --json nameWithOwner -q .nameWithOwner)
BASE=$(gh repo view --json defaultBranchRef -q .defaultBranchRef.name)
VIS=$(gh repo view --json visibility -q .visibility)   # PUBLIC / PRIVATE / INTERNAL
echo "$REPO ($BASE) $VIS"
```

- Команда впала (не git-репозиторій, немає remote на GitHub, немає доступу) — скажи про це прямо
  й зупинись. Не підставляй репозиторій навмання.
- Користувач явно назвав інший репозиторій (`owner/name` або URL тікета) — використай його.
  Посилання `https://github.com/owner/name/issues/42` дає і `REPO`, і `ISSUE`.
- Немає `$ISSUE` і номер не названо — спитай.

Далі в усіх командах `gh` передавай `-R "$REPO"`, щоб не залежати від того, куди дивиться
`gh` за замовчуванням (форки, кілька remote).

Обовʼязково має бути лейбл `spec:approved`, поставлений **людиною**. Перевір, хто його поставив:

```bash
gh api "repos/$REPO/issues/$ISSUE/events" \
  -q '.[] | select(.event=="labeled" and .label.name=="spec:approved") | {who: .actor.login, type: .actor.type, at: .created_at}'
```

Немає `spec:approved` або його поставив бот (`type: Bot`, або це ти сам) — зупинись, нічого не роби,
напиши чому. Не апрувай сам.

Постав `ai:in-progress` (`gh issue edit $ISSUE -R "$REPO" --add-label ai:in-progress`), зніми наприкінці.
Якщо лейбла в репозиторії ще немає — створи його (`gh label create "ai:in-progress" -R "$REPO"`);
немає прав — продовжуй і згадай про це в підсумку.

## Крок 1. Прочитай правила проєкту

Стек, тести й заборони в кожному репозиторії свої, тому не бери їх із голови — прочитай
з репозиторію (що є):

- `CLAUDE.md` (у корені та в теках, які будеш зачіпати), `AGENTS.md`;
- `CONTRIBUTING.md`, `README.md`, `.github/pull_request_template.md`;
- `package.json` / `pyproject.toml` / `pom.xml` / `build.gradle` / `go.mod` тощо, конфіги лінтерів;
- наявні тести — щоб побачити фреймворк, теку й стиль.

З цього склади короткий робочий перелік:

- **стек і залежності** — що дозволено, чи можна додавати нові (за замовчуванням — ні);
- **тести** — фреймворк, тека, команда запуску всієї сюїти;
- **докази для UI** — чи є в проєкті скрипт для скріншотів (напр. `scripts/evidence.*`) і куди вони лягають;
- **конвенції** — стиль, мова інтерфейсу й коментарів, адаптивність, доступність тощо;
- **заборонені зони** — теки й файли, які не можна чіпати.

Якщо явних правил немає — орієнтуйся на стиль сусіднього коду й прямо напиши в PR,
що конвенції виведено з коду, а не з документа.

## Крок 2. Перечитай специфікацію

```bash
gh issue view $ISSUE -R "$REPO" --comments
```

Знайди останній коментар зі специфікацією і **всі** зауваження людини після нього.
Якщо людина щось уточнила в коментарях після специфікації — це частина завдання.

Специфікація — межа роботи. Усе, що в «Поза межами», не робиться, навіть якщо руки сверблять.

## Крок 3. Спочатку тести

На кожен пункт «Критеріїв приймання» — окремий тест у фреймворку й теці, які вже використовує
проєкт (Playwright, Jest, pytest, JUnit — що є). Новий тестовий фреймворк не вводь, якщо
проєкт цього прямо не дозволяє.

Запусти їх до реалізації: вони мають падати. Так ти знаєш, що вони справді щось перевіряють.
Збережи текст падіння — він знадобиться для PR.

Якщо в проєкті взагалі немає тестової інфраструктури — не вигадуй її, постав `needs-human`
і поясни, чим можна довести критерії.

## Крок 4. Реалізуй

```bash
git fetch origin --prune
git switch -c "ai/$ISSUE-<короткий-опис>" "origin/$BASE"
```

Тримайся правил проєкту з Кроку 1. Нових залежностей не додавай, якщо правила цього прямо не дозволяють.

Якщо під час роботи зʼясувалося, що специфікація неможлива або помилкова — **зупинись**,
постав `needs-human`, поясни в коментарі що саме не сходиться. Не переписуй завдання на ходу.

## Крок 5. Доведи

1. Запусти всю сюїту командою проєкту (`npm test`, `pytest`, `mvn test`, `make test` — що вказано в правилах).
2. Для UI-змін — скріншоти десктоп **і** мобільний:
   - є скрипт доказів у проєкті — використай його (наприклад,
     `node scripts/evidence.mjs feature-$ISSUE` і `... --mobile`);
   - немає — зроби скріншоти тим інструментом, що вже є в проєкті (напр. Playwright), і поклади їх
     у `docs/evidence/feature-$ISSUE-*.png` або в теку, яку вказують правила.

   Скріншоти комітяться в гілку PR. Для не-UI змін скріншоти не потрібні — достатньо тестів.
   Для платформи без UI-автотестів і скрипта скріншотів (напр. нативний застосунок лише з
   unit-тестами) скріншоти не вигадуй — перенеси її пункти в розділ PR «Перевірити людині».
3. Склади посилання на скріншоти за видимістю репозиторію (`$VIS` з Кроку 0):
   - **PUBLIC** → `https://raw.githubusercontent.com/$REPO/<гілка>/docs/evidence/<файл>.png`
   - **PRIVATE / INTERNAL** → `https://github.com/$REPO/blob/<гілка>/docs/evidence/<файл>.png?raw=true`

   `raw.githubusercontent.com` у приватному репо без токена не відкривається — у PR будуть биті
   картинки. `blob/...?raw=true` показує картинку всім, хто має доступ до репозиторію.

## Крок 6. PR

Запуш гілку й відкрий draft PR у `$BASE`. Тіло — файлом (`--body-file`), не `--body`.
Якщо в репозиторії є `.github/pull_request_template.md` — дотримуйся його, додавши секції нижче.

```markdown
Fixes #$ISSUE

## Що зроблено
Коротко, за специфікацією з #$ISSUE.

## Критерії приймання
| Критерій | Тест | Статус |
|---|---|---|
| <критерій зі специфікації> | `<шлях/до/тесту>:<рядок>` | ✅ |

## Докази
Тести до реалізації падали: <коротко текст падіння>.
Уся сюїта: N passed.

<!-- лише для UI -->
| Десктоп | Мобільний |
|---|---|
| ![десктоп](<IMG_URL feature-$ISSUE-result.png>) | ![мобільний](<IMG_URL feature-$ISSUE-result-mobile.png>) |

## Перевірити людині
Чекліст зі специфікації плюс те, що виявилось під час роботи: платформа, що натиснути, що
побачити, де найбільший ризик (файл:рядок). Нема — «нема».

## Поза межами
Перелічи, що свідомо не робив (зі специфікації).

<sub>🤖 Автоматична імплементація · рев'ю — `agent:go`, мердж — Approve + `agent:go`</sub>
```

`<IMG_URL файл>` — посилання з Кроку 5, п. 3 (формат залежить від `$VIS`). Підстав реальні `$REPO`,
гілку й шляхи, куди поклав скріншоти: GitHub змінні не розкриє.

```bash
gh pr create -R "$REPO" --draft --base "$BASE" --title "<назва>" --body-file pr.md
gh pr ready <номер> -R "$REPO"          # коли все зелено
```

Коментар у тікет із посиланням на PR, зняти `ai:in-progress`.

## Заборонено

Починати без `spec:approved`, виходити за межі специфікації, мерджити,
пушити в `$BASE` (`main`/`master`/`develop`), міняти `.github/`, `.claude/`, CI-конфіги
та інші заборонені зони з правил проєкту.

# Додаток: докази і GitHub

- Ієрархія доказів: падаючий → зелений тест > зелена сюїта > скріншот (доповнює, не замінює).
- Обовʼязковий мінімум для фічі (якщо в правилах проєкту не вказано інше): тест на кожен критерій +
  зелена сюїта; для UI — ще скріншот десктоп і мобільний.
- Здався (`needs-human`): що пробував + що побачив + 2–3 гіпотези з посиланнями на рядки.
- Скріншоти комітяться в гілку PR і показуються лише посиланням на файл у гілці (формат — за `$VIS`, Крок 5), не артефакти Actions.
- Після мерджу гілку видаляють — перед цим переведи посилання на скріншоти з `<гілка>` на `$BASE`, інакше картинки зламаються.
- Чесність: тест не запускався — так і напиши; вигаданий результат прогону знищує довіру.
- Перед висновками про гілки: `git fetch origin --prune && git log --oneline -5 "origin/$BASE"`.
- Довгі коментарі та тіла PR — через `--body-file`, не `--body`.
- Захист від циклів: якщо останній коментар від бота або від тебе — зупинись, якщо людина прямо не попросила.
- `ai:in-progress` знімається **за будь-якого** результату.
