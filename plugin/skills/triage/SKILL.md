# Тріаж тікета

## Пріоритет проєкту

- Конвенції репозиторію з `CLAUDE.md` / `AGENTS.md` (у корені й у теках, яких торкаєшся) мають
  **пріоритет над цим скілом**: команди встановлення й тестів, стиль, заборони, формат комітів і PR.
  Скіл не знає стеку проєкту — бери його з `CLAUDE.md` / README, а не з голови.
- Мова коментарів, опису PR і специфікації — **мова тікета**, якщо `CLAUDE.md` не каже інакше.
  Приклади формулювань нижче — українською лише як зразок.
- Шлях і спосіб доказів (скріншоти, логи) — з `CLAUDE.md`; за замовчуванням `docs/evidence/`.
- Службові маркери пиши **дослівно, незалежно від мови тексту** (`## 🔍 Тріаж`, `❓ Потрібно уточнити`,
  підписи `<sub>🤖 …`, `<!-- kando:draft-reason: … -->`, рядок «Схвалення в Kando: @… на коміті …»
  з промпту): за ними Kando і наступні запуски розпізнають коментарі й стан.
- Пріоритет проєкту стосується стилю, мови, команд і місця та формату доказів, але **не скасовує
  запобіжників скіла**: гейт мерджу (`ai:reviewed` на поточному коміті, Approve людини на поточному
  sha — зокрема правило рядка «Схвалення в Kando: …» — і зелений CI), вимоги надати докази,
  службові маркери та заборону чіпати файли поза завданням. `CLAUDE.md` цього не знімає.

Ти перший агент у пайплайні. Твоя робота — **класифікувати й перевірити повноту**, не виправляти.

Скіл не привʼязаний до конкретного репозиторію: працюй із тим репозиторієм, у якому тебе викликали.

## Запуск від диспетчера agent-flow

Якщо в запиті є блок «Контекст запуску (диспетчер agent-flow)», це **явна команда людини**:

- `REPO`, `ISSUE`, `PR` бери з першого рядка запиту, а не з робочої директорії.
- Умови «зупинись, якщо …» з Кроку 0б не діють, **крім** закритого тікета. Захист від циклів
  («останній коментар від бота — стоп») і перевірка ідемпотентності теж не діють.
  `implement`: перевірку, що `spec:approved` поставила людина, виконуй як завжди.
- Лейбли `agent:*` не чіпай — ними керує диспетчер. `ai:in-progress` став і знімай, як описано нижче.
- **Режим `rework`**: прочитай коментарі людей, написані після твого останнього коментаря
  (підписаного `<sub>🤖`; службові коментарі `<sub>🤖 agent-flow</sub>` не враховуй), — для PR також коментарі до рядків і тіла рев'ю. Це завдання на доопрацювання.
  Опублікуй **новий** коментар у тому самому форматі з позначкою «(оновлено)» в заголовку
  і блоком **«Що змінилося»** — список змін відносно попередньої версії. Рядок з маркером
  питань починай з нього лише тоді, коли питання справді лишились.

## Крок 0а. Визнач репозиторій і тікет

Репозиторій бери з поточної робочої директорії, а не з памʼяті чи прикладів:

```bash
gh auth status
REPO=$(gh repo view --json nameWithOwner -q .nameWithOwner)
BASE=$(gh repo view "$REPO" --json defaultBranchRef -q .defaultBranchRef.name)
echo "$REPO ($BASE)"
```

- Якщо команда впала (не git-репозиторій, немає remote на GitHub, немає доступу) — скажи
  про це прямо й зупинись. Не підставляй репозиторій навмання.
- Якщо користувач явно назвав інший репозиторій (`owner/name` або URL тікета) — використай його.
- Посилання на кшталт `https://github.com/owner/name/issues/42` дає і `REPO`, і `ISSUE`.

Номер тікета — у `$ISSUE`. Якщо змінна порожня і номер не названо — спитай його в користувача.

Далі в усіх командах `gh` передавай `-R "$REPO"`, щоб не залежати від того, куди
дивиться `gh` за замовчуванням (форки, кілька remote). Основну гілку бери з `$BASE` —
вона не завжди `main`.

## Крок 0б. Перевір, чи треба працювати

```bash
gh issue view $ISSUE -R "$REPO" --json number,title,body,labels,author,state
```

Зупинись і нічого не роби, якщо:

- тікет закритий;
- уже є лейбл `ai:triaged` (хіба що людина зняла його або прямо попросила перетріажити);
- є лейбл `ai:in-progress` — над ним працює інший агент;
- є лейбл `needs-human` і немає явної команди людини.

Ці зупинки відбуваються до взяття задачі в Kando: відпускати нічого.

Людина прямо наказала перебрати задачу (наприклад, попередню сесію вбито, і лейбл лишився): зупинка через `ai:in-progress` не діє. Перейди до кроку «взяти задачу в Kando» і додай до команди `--takeover`. Вивід «закріплено» доводить, що лейбл застарілий: працюй далі. Будь-який інший вивід цього не доводить: зупинись і передай його людині.

## Крок: взяти задачу в Kando

Пропусти цей крок і крок «Відпустити задачу в Kando» нижче, якщо в запиті є блок «Контекст запуску (диспетчер agent-flow)», або якщо команда нижче показана з незаміненими змінними `CLAUDE_…` чи файла скрипта немає (інший редактор).

```bash
"${CLAUDE_PLUGIN_ROOT}/bin/kando-session" begin --session "${CLAUDE_SESSION_ID}" --repo "$REPO" --number <N> --skill triage
```

`<N>` — номер тікета (`$ISSUE`). `$REPO` — репозиторій, з яким працює скіл; якщо змінна не збереглась між командами, підстав значення. Виконай це до будь-якої зміни стану: лейбла, коментаря, гілки.

Код виходу `3` означає, що задачу вже тримає хтось інший: зупинись, нічого не змінюй і передай людині вивід. Якщо задачу тримає інша твоя сесія (вивід це скаже) і людина вирішить її перебрати, повтори команду з `--takeover`; лише за явним рішенням людини, ніколи з власної ініціативи. Чужу сесію чи запуск Kando перебрати не можна. Будь-який інший результат — працюй далі.

Якщо інструмент чи хук повідомляє, що задачу втрачено, — зупинись, нічого не пуш, не змінюй PR і не чіпай лейбли, скажи про це людині й не запускай `begin` повторно без її рішення. У цьому випадку `end` **не виконуй**: стан сесії має лишитись, щоб перевірка перед пушем і далі блокувала команди. Виняток: людина прямо вирішила кинути задачу. Тоді виконай `end`: стан зникне, і пуші в цьому репо більше не блокуватимуться. Сам цього не роби.

Відпускай задачу (крок «Відпустити задачу в Kando») і на кожному шляху зупинки після взяття, не лише в кінці, крім випадку, коли задачу втрачено.

## Крок 0в. Познач початок роботи

Постав `ai:in-progress` і працюй. Знімай його в кінці **завжди**, навіть при помилці.

## Крок 1. Класифікуй

| Тип | Ознаки |
|---|---|
| `type:bug` | описана поведінка, що відрізняється від очікуваної; є слова «не працює», «ламається», «помилка» |
| `type:feature` | прохання додати або змінити поведінку, якої зараз немає |
| `type:other` | питання, документація, ідея без конкретики, спам |

Сумніваєшся між багом і фічею — дивись, чи існує описана функціональність зараз.
Якщо її нема — це фіча, навіть коли автор пише «баг».

## Крок 2. Перевір повноту — і запропонуй рішення

Для `type:bug` мусять бути: кроки відтворення, очікуваний результат, фактичний результат, браузер.
Для `type:feature` мусять бути: хто/навіщо, що саме, критерії приймання.

Чогось бракує — **не зупиняйся на питанні**. Спочатку прочитай код (крок 4), а тоді на кожну
прогалину дай конкретну відповідь від себе. Не «де має жити перемикач?», а «пропоную іконку
в шапці праворуч від заголовка: місце вже є, на 360px не ламається».

Пропозиція мусить бути такою, щоб на неї можна було відповісти «так» або одним рядком правки:

- **один** основний варіант, а не меню з п'яти;
- коротке «чому саме так» з опорою на код або конвенції з `CLAUDE.md`;
- явно позначена як припущення агента, а не як слова автора.

Питання став лише там, де пропозиція була б чистим вгадуванням: коли різні відповіді дають
**різні продукти**, і код не підказує, який саме потрібен.

Якщо без автора рушити неможливо (тікет незрозумілий або це баг без кроків, який ти не відтворив),
**не став** `needs-info`: постав тип і `ai:triaged`, а питання винеси в розділ «❓ Потрібно уточнити»
коментаря. Диспетчер не пустить задачу далі, доки людина не відповість і не поставить `agent:rework`.

## Крок 3. Пошукай дублікати

```bash
gh issue list -R "$REPO" --state all --limit 50 --json number,title,state
```

Схожий тікет — згадай його в коментарі («схоже на #7»), але **не закривай** нічого сам.

## Крок 4. Прочитай проєкт

Перед висновком прочитай `CLAUDE.md` і файл, якого стосується тікет. Тріаж без читання коду — вгадування.
Пропозиція з кроку 2 без читання коду — вгадування вдвічі.

## Крок 5. Напиши коментар

Формат — рівно такий:

```markdown
## 🔍 Тріаж

**Тип:** баг
**Що зрозуміло:** коротко, 1–2 речення своїми словами.
**Ймовірна зона в коді:** `<файл>:<функція>` — з поясненням чому саме там.
**Чого бракує:** список або «все на місці».
**Пропозиція:** що пропонуєш на кожну прогалину і чому; «не потрібна», якщо все на місці.
**Схожі тікети:** #7 або «не знайдено».
**❓ Потрібно уточнити:** питання, без відповіді на які рухатись не можна (рядок лише за потреби).

**Далі:** 👤 перевір тріаж. Усе гаразд — постав `agent:go`. Щось не так — коментар + `agent:rework`.

<sub>🤖 Автоматичний тріаж · [як працює пайплайн](../blob/<BASE>/PIPELINE.md)</sub>
```

У підписі підстав реальну назву основної гілки замість `<BASE>`. Якщо `PIPELINE.md` у корені
репозиторію немає — прибери посилання і залиш лише «🤖 Автоматичний тріаж».

## Крок: відпустити задачу в Kando

Пропусти цей крок, якщо в запиті є блок «Контекст запуску (диспетчер agent-flow)», або якщо команда нижче показана з незаміненими змінними `CLAUDE_…` чи файла скрипта немає (інший редактор). Виконай крок наприкінці роботи і на кожному шляху зупинки після взяття. Винятки: код `3` (задачу не взято) і втрачена задача (стан має лишитись, хіба що людина вирішила кинути задачу) — тоді `end` не виконуй:

```bash
"${CLAUDE_PLUGIN_ROOT}/bin/kando-session" end --session "${CLAUDE_SESSION_ID}"
```

Результат команди не впливає на роботу.

# Додаток: робота з GitHub із хмарної сесії

## Перевірка доступу

Перше, що робить агент (це частина кроку 0а):

```bash
gh auth status && gh repo view "$REPO" --json name
```

Немає доступу — зупинись і скажи про це прямо. Не вдавай, що працюєш.

## Спочатку — свіжий стан репозиторію

Чекаут у хмарній сесії приходить у **detached HEAD**, а `origin/*` у ньому можуть бути
застарілими. Тому **перед будь-яким висновком** про стан гілок:

```bash
git fetch origin --prune
git log --oneline -5 "origin/$BASE"
```

Якщо після `git fetch` розбіжність залишилась — вона справжня, тоді зупиняйся і клич людину.

## Часті команди

```bash
gh issue view $ISSUE -R "$REPO" --comments
gh issue list -R "$REPO" --label "type:bug" --label "ai:triaged" --state open --json number,title
gh issue comment $ISSUE -R "$REPO" --body-file коментар.md
gh issue edit $ISSUE -R "$REPO" --add-label "x" --remove-label "y"
gh pr create -R "$REPO" --draft --title "..." --body-file тіло.md
gh pr ready $PR -R "$REPO"
gh pr checks $PR -R "$REPO"
gh pr comment $PR -R "$REPO" --body-file рев'ю.md
```

Довгі коментарі завжди через `--body-file`, а не `--body`: лапки й переноси
в українському тексті ламають шелл.

## Захист від циклів

Перед роботою перевір автора останнього коментаря. Якщо це бот або ти сам —
зупинись, окрім випадку, коли людина прямо попросила продовжити.

## Ідемпотентність

Запуск може повторитися. Перед публікацією коментаря перевір, чи такого ще немає:

```bash
gh issue view $ISSUE -R "$REPO" --comments --json comments -q '.comments[].body' | grep -c "## 🔍 Тріаж"
```

Уже є — онови наявний коментар замість дубля, або просто вийди.

## Завжди прибирай за собою

Лейбл `ai:in-progress` знімається **за будь-якого** результату: успіх, помилка, здача.
Залишений `ai:in-progress` блокує тікет назавжди.
