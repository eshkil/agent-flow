# Робота з багом

Порядок незмінний: **відтворити → зафіксувати тестом → виправити → довести**.
Фікс без відтворення заборонений: ти не знаєш, що саме лагодиш.

Скіл не привʼязаний до конкретного репозиторію: працюй із тим репозиторієм, у якому
тебе викликали. Номер тікета — у `$ISSUE`.

## Запуск від диспетчера agent-flow

Якщо в запиті є блок «Контекст запуску (диспетчер agent-flow)», це **явна команда людини**:

- `REPO`, `ISSUE`, `PR` бери з першого рядка запиту, а не з робочої директорії.
- Умови «зупинись, якщо …» з Кроку 0 не діють, **крім** закритого тікета. Захист від циклів
  («останній коментар від бота — стоп») і перевірка ідемпотентності теж не діють.
  `implement`: перевірку, що `spec:approved` поставила людина, виконуй як завжди.
- Лейбли `agent:*` не чіпай — ними керує диспетчер. `ai:in-progress` став і знімай, як описано нижче.
- **Режим `rework`**: прочитай коментарі людей, написані після твого останнього коментаря
  (підписаного `<sub>🤖`), — для PR також коментарі до рядків. Це завдання на доопрацювання.
  Опублікуй **новий** коментар у тому самому форматі з позначкою «(оновлено)» в заголовку
  і блоком **«Що змінилося»** — список змін відносно попередньої версії.

## Крок 0. Визнач репозиторій, базову гілку і стан

Репозиторій бери з поточної робочої директорії, а не з памʼяті чи прикладів:

```bash
gh auth status
REPO=$(gh repo view --json nameWithOwner -q .nameWithOwner)
BASE=$(gh repo view --json defaultBranchRef -q .defaultBranchRef.name)
VIS=$(gh repo view --json visibility -q .visibility)
echo "$REPO $BASE $VIS"
git fetch origin --prune && git log --oneline -5 origin/$BASE
```

- Команда впала (не git-репозиторій, немає remote на GitHub, немає доступу) — скажи про це
  прямо й зупинись. Не підставляй репозиторій навмання.
- Якщо користувач явно назвав інший репозиторій (`owner/name` або URL тікета) — використай його.
  Посилання `https://github.com/owner/name/issues/42` дає і `REPO`, і `ISSUE`.
- `$ISSUE` порожній і номер не названо — спитай у користувача.

Далі в усіх командах `gh` передавай `-R "$REPO"` (форки, кілька remote), а базову гілку
називай `$BASE`, а не `main` — у проєкті це може бути `master`, `develop` тощо.

**Стан тікета.** Працюй лише якщо є `type:bug` + `ai:triaged`, і немає `ai:in-progress`,
`needs-human`. Постав `ai:in-progress`, зніми його наприкінці за будь-якого результату.
Якщо потрібного лейбла в репозиторії немає, `gh issue edit` впаде — створи його
(`gh label create "<лейбл>" -R "$REPO"`) і повтори; немає прав — повідом у підсумку.

### Правила саме цього проєкту

Команди встановлення, запуску тестів, стек і заборони в кожному репозиторії свої —
прочитай їх із репозиторію, а не з голови (що є):

- `CLAUDE.md` (у корені та в теках, які зачіпає баг), `AGENTS.md`;
- `CONTRIBUTING.md`, `README.md`, `.github/pull_request_template.md`;
- `package.json` / `pyproject.toml` / `pom.xml` тощо, конфіги тестів (`playwright.config.*` та ін.).

Склади короткий перелік, яким користуватимешся далі:

| Що | Звідки / за замовчуванням |
|---|---|
| `INSTALL` — встановлення залежностей | з README/CLAUDE.md; для Node — `npm ci` або `npm install` |
| `TEST` — уся сюїта | скрипт `test` у `package.json` або аналог |
| Теки й фреймворк тестів | де вже лежать e2e/UI-тести (часто `tests/`, `e2e/`) |
| Як робити скріншоти-докази | `scripts/evidence.mjs`, якщо є; інакше — див. додаток «Правила доказів» |
| Критичні інваріанти й заборони | структури даних, API-контракти, теки, які не можна чіпати |
| Мова коментарів, стиль комітів | з документів або з історії `git log` |

Явних правил немає — орієнтуйся на сусідній код і прямо напиши в PR, що конвенції
виведено з коду, а не з документа.

## Крок 1. Відтвори

Встанови залежності командою `INSTALL` і браузер для Playwright
(`npx playwright install --with-deps chromium`, якщо його ще немає).

Виконай кроки з тікета **буквально**, у браузері через Playwright. Не переказуй їх — виконуй.
Застосунок запускай так, як описано в проєкті (dev-сервер, статичний файл, `webServer` у
конфігу Playwright тощо).

Якщо кроків бракує або вони суперечливі — не вигадуй. Постав `needs-human`,
напиши, який саме крок не вдалося виконати й чому.

**Не відтворилося?** Постав `bug:not-reproducible`, напиши коментар із:
що саме ти зробив (список команд і дій), що побачив натомість, скріншот поточної поведінки,
і 2–3 уточнювальні питання авторові. Не закривай тікет.

**Відтворилося?** Постав `bug:reproduced`, зроби скріншот «до» і **одразу опублікуй його в тікеті**:

```bash
BRANCH=ai/$ISSUE-<короткий-опис>
git checkout -b $BRANCH origin/$BASE                      # гілка потрібна вже тут
# скріншот «до» — див. «Як робити скріншоти»; файл: docs/evidence/before-$ISSUE-result.png
git add docs/evidence/before-$ISSUE-*.png && git commit -m "docs: доказ відтворення #$ISSUE"
git push -u origin $BRANCH
```

Коментар у тікет — **до того, як почнеш лагодити** (посилання на картинку — див.
«Як показати скріншот у коментарі»):

```markdown
## 🔁 Баг відтворено

**Як відтворював:** що саме зробив, по кроках.
**Що побачив:** фактична поведінка.

![до](<IMG_URL before-$ISSUE-result.png>)

**Далі:** фіксую тестом і виправляю / передаю людині (якщо впевненість низька).
```

Це доказ, що баг існує. Він має зʼявитися в тікеті **раніше** за будь-який фікс —
щоб автор бачив підтвердження, навіть якщо далі робота впреться в `needs-human`.

## Крок 2. Зафіксуй тестом

Напиши тест, який **падає через цей баг**, — у тій теці й тим фреймворком, де в проєкті вже
живуть браузерні тести (зазвичай Playwright). Запусти, переконайся що червоний, скопіюй
текст падіння — він піде в коментар. Тест, який не падав до фікса, нічого не доводить.

Якщо в проєкті немає браузерних тестів, напиши падаючий тест на найнижчому рівні, де баг
ще проявляється, в наявному тестовому фреймворку. Додавати новий тестовий фреймворк
або залежність заради цього — не можна: це продуктове рішення → `needs-human`.

## Крок 3. Оціни впевненість

Виправляй сам **тільки якщо виконані всі** умови:

- причина локалізована до конкретної функції або рядка (не «десь у app.js»);
- є падаючий тест із кроку 2;
- фікс зачіпає ≤ 2 файли й не змінює критичних інваріантів проєкту (структури даних,
  API-контракти, схеми — див. «Правила саме цього проєкту»);
- немає продуктового вибору між кількома варіантами поведінки.

**Хоч одна не виконана** → постав `needs-human`, зніми `ai:in-progress` і напиши коментар:
відтворення, падаючий тест, 2–3 гіпотези причини з посиланнями на рядки, що саме заблокувало.
Це нормальний і очікуваний результат, а не поразка.

## Крок 4. Виправ

Гілка: `$BRANCH` від свіжого `origin/$BASE`. Ніколи не комить у `$BASE`.

Мінімальна зміна, що робить тест зеленим. Не рефактори поряд, не «покращуй» сусідній код,
не додавай залежностей. Дотримуйся конвенцій проєкту з Кроку 0.

## Крок 5. Доведи

Запусти **всю** сюїту командою `TEST` — зелена має бути вся, не тільки новий тест.
Потім зроби скріншот «після» (`docs/evidence/after-$ISSUE-result.png`) тим самим способом,
що й «до».

Якщо баг невидимий на звичайному скріншоті (фокус, aria, стан у памʼяті) — підсвіти стан,
як описано в додатку «Правила доказів». Дві однакові картинки — не доказ; або зроби різницю
видимою, або чесно скажи, що скріншот тут нерелевантний.

Обидва скріншоти (`before-*`, `after-*`) закомить у гілку разом із фіксом.

## Крок 6. Створи PR

```bash
git push -u origin $BRANCH
gh pr create -R "$REPO" --base "$BASE" --head "$BRANCH" --draft \
  --title "fix: <опис> (#$ISSUE)" --body-file pr-body.md
```

Якщо в проєкті є `.github/pull_request_template.md` — дотримуйся його розділів, додавши
до них усе, що нижче. Інакше тіло PR:

````markdown
Fixes #$ISSUE

## Причина
Що саме ламалося і чому, з посиланням на `файл:рядок`.

## Виправлення
Що змінено і чому саме так.

## Докази
Тест `<шлях до тесту>` падав до фікса:
```
<текст падіння>
```
Після фікса вся сюїта зелена: N passed.

| До | Після |
|---|---|
| ![до](<IMG_URL before-$ISSUE-result.png>) | ![після](<IMG_URL after-$ISSUE-result.png>) |

## Ризики
Що могло зачепитися і чому вважаєш, що ні.

<sub>🤖 Автоматичний фікс · рев'ю — `agent:go`, мердж — Approve + `agent:go`</sub>
````

Коли тести зелені — зніми draft: `gh pr ready <номер> -R "$REPO"`.

## Крок 7. Закрий цикл

Другий коментар у **тікеті** — зі скріншотом «після». Разом із коментарем «до» з кроку 1
вони утворюють пару, яку автор бага бачить не відкриваючи PR:

```markdown
## ✅ Виправлено, чекає рев'ю

**Що було:** одне речення про причину.
**Що зроблено:** одне речення про фікс.

![після](<IMG_URL after-$ISSUE-result.png>)

Тест `<шлях до тесту>` падав до фікса, тепер зелений. Уся сюїта: N passed.
PR: #<номер> — рев'ю — `agent:go`, мердж — Approve + `agent:go`.
```

Далі зніми `ai:in-progress`.
**Тікет не закривай** — він закриється сам при мерджі PR людиною.

## Заборонено

Мерджити PR, пушити в `$BASE`, правити `.github/` і `.claude/`,
заявляти «виправлено» без зеленого прогону, видаляти чужі тести щоб стало зелено.

# Додаток: правила доказів

Заявка «працює» без доказу не приймається.

## Ієрархія доказів

1. **Падаючий → зелений тест.** Єдиний доказ, що щось справді виправлено.
2. **Зелена сюїта.** Доказ, що нічого не зламано поряд.
3. **Скріншот.** Доказ, що це виглядає так, як заявлено. Доповнює тест, не замінює.

## Як робити скріншоти

**Якщо в проєкті є власний скрипт доказів** (наприклад, `scripts/evidence.mjs`) —
використовуй його; перевір параметри в самому скрипті або в `CLAUDE.md`. Типовий вигляд:

```bash
node scripts/evidence.mjs before-$ISSUE --test <id>
node scripts/evidence.mjs after-$ISSUE --test <id>
node scripts/evidence.mjs after-$ISSUE --mobile    # мобільний вʼюпорт
node scripts/evidence.mjs after-$ISSUE --focus     # підсвічує, де фокус клавіатури
```

**Якщо скрипта немає** — знімай скріншот прямо з Playwright у тому ж сценарії, що
відтворює баг, і клади у `docs/evidence/` (або в теку, прийняту в проєкті):

```js
await page.screenshot({ path: `docs/evidence/before-${ISSUE}-result.png`, fullPage: true });
```

Тимчасові скрипти для скріншотів не коміть — у гілку йдуть лише картинки, тест і фікс.

### Коли баг не має візуального прояву

Фокус, aria-атрибути, стан у памʼяті, порядок обходу — цього на звичайному скріншоті не видно,
і «до»/«після» виходять однаковими. Однакові картинки — це не доказ, а шум.

У такому разі **зроби стан видимим**:

- фокус клавіатури → прапорець `--focus` скрипта доказів, або перед скріншотом намалюй через
  `page.evaluate` рамку навколо `document.activeElement` і плашку з його описом;
- інший невидимий стан → так само виведи його на сторінку перед скріншотом.

Якщо візуалізувати стан неможливо — прямо напиши, що скріншот тут нерелевантний.

Файли **комітяться в гілку PR**.

## Куди класти скріншоти

| Куди | Коли | Що саме |
|---|---|---|
| **Тікет** | одразу після відтворення, **до фікса** | скріншот «до» — доказ, що баг існує |
| **Тікет** | після фікса | скріншот «після» + посилання на PR |
| **PR** | при створенні | повний набір «до» + «після» і текст падаючого тесту |

Обидва коментарі в тікеті обовʼязкові. Сухе посилання на PR замість скріншота не приймається.

## Як показати скріншот у коментарі

Тільки через посилання на файл у гілці. `<IMG_URL файл>` у шаблонах вище — це повне посилання
на конкретний файл; формат залежить від видимості репозиторію (`$VIS`):

- **PUBLIC** → `https://raw.githubusercontent.com/$REPO/$BRANCH/docs/evidence/<файл>`
- **PRIVATE / INTERNAL** → `https://github.com/$REPO/blob/$BRANCH/docs/evidence/<файл>?raw=true`
  (raw.githubusercontent.com у приватному репо без токена не відкриється, а `blob/...?raw=true`
  показує картинку всім, хто має доступ до репо). `?raw=true` — обовʼязково в кінці: без нього
  `blob/...` веде на HTML-сторінку, і картинка буде битою.

Підставляй реальні значення `$REPO` і `$BRANCH` у текст коментаря — GitHub змінні не розкриє.
Що файл існує, перевіряй через `gh api "repos/$REPO/contents/docs/evidence/<файл>?ref=$BRANCH"`,
а не curl — у приватному репо curl дасть 404 навіть для правильного посилання.
Після мерджу гілку видаляють — перед цим посилання в тікеті й PR переводять з `$BRANCH` на `$BASE`,
інакше картинки зламаються.
Артефакти GitHub Actions **не годяться** — їх не видно в коментарі.

## Обовʼязковий мінімум

| Випадок | Докази |
|---|---|
| Баг виправлено | падаючий тест (текст падіння) + зелена сюїта + скріншоти «до» і «після» |
| Баг не відтворився | список виконаних кроків + скріншот поточної поведінки + питання авторові |
| Здався (`needs-human`) | що пробував + що побачив + 2–3 гіпотези з посиланнями на рядки |

Якщо правила проєкту вимагають більше — виконуй правила проєкту.

## Чесність

Тест не запускався — так і напиши. Скріншот не вийшов — напиши чому.
Вигаданий результат прогону знищує довіру до всього пайплайну.

# Додаток: GitHub

- Усі команди `gh` — з `-R "$REPO"`; базова гілка — `$BASE` з Кроку 0.
- Перед висновками про гілки: `git fetch origin --prune && git log --oneline -5 origin/$BASE`
  (чекаут може бути detached HEAD із застарілими `origin/*`).
- Довгі коментарі — через `--body-file`, не `--body`.
- Захист від циклів: якщо останній коментар від бота або від тебе — зупинись, якщо людина прямо не попросила продовжити.
- Ідемпотентність: перед публікацією перевір, чи такого коментаря ще немає; є — онови або вийди.
- `ai:in-progress` знімається **за будь-якого** результату.
